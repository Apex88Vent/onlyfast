# Kart setup sheets and class-selection navigation

Completed October 1, 2026 (Pacific time). The additive backend migration is applied to the verified production project `thpyjvwtfvfxiufchrxn`. The tested frontend is local and ready for the user's manual GitHub push; it has not been deployed to production by this task.

2. **Migration.** `supabase/migrations/20261002030004_add_development_kart_classes.sql`. Created through `supabase migration new`, applied with the Supabase migration tool, and aligned to its recorded version `20261002030004`. The already-deployed `20260930_add_development_setup_library.sql` remains unchanged. Only the existing classification and canonicalization functions are replaced with their prior lists plus two kart names. Existing function privileges, RLS, triggers, summary filtering, feature flags and account rows are retained. Prerequisites are checked; the migration passes twice in isolated PostgreSQL.

3. **Canonical identifiers.** The architecture uses canonical class names as identifiers: `Shifter Kart` and `Clutch Kart`. Category `road_course`; family `kart`. There is no separate kart discipline or database taxonomy table. Field identifiers are stable snake_case keys, with existing section/class/category/unit metadata and the existing `onlyfast_setup_library_v1` snapshot format.

4. **Sections and fields.** Both have 11 dedicated sections and 72 declared fields, plus the existing common Notes field. General, four-corner Tires, Front End, Rear End, Seat, Chassis, Ackerman / Steering, Gearing, Engine and Brakes are shared. Each has one additional two-field section described below. The complete field inventory follows this report.

5. **Shared groups.** `kartGeneral`, `kartTires`, `kartFrontGeometry`, `kartRearAxle`, `kartSeat`, `kartChassis`, `kartSteering`, `kartGearing`, `kartEngine`, `kartBrakes`. Fields cover frame flex, axle/hub/bearing settings, geometry and track width; the sheets do not inherit car springs, dampers, differential or anti-roll-bar fields.

6. **Differences.** Shifter Kart adds `kartShifterBrakes`: front brake/pad configuration and front brake balance where adjustable, alongside shared rear brakes/pedal settings. Clutch Kart adds `kartClutchDrive`: centrifugal-clutch/direct-drive configuration and centrifugal clutch engagement RPM. Its braking fields are rear brake/pad configuration and pedal position/free play. Both record drive/rear sprockets and final ratio. Individual adjustable gearbox ratios are not assumed. Optional engine map, carburetor/jetting and exhaust fields identify when fitted, adjustable or permitted. No manufacturer-specific defaults are supplied.

   Geometry, axle/hub and seat tuning are supported by the manufacturer's [KZ setup reference](https://www.birelart.com/public/karts/modelli/pdf/5/Setup%20Kart%20KZ.pdf). The brake distinction follows its [KZ specifications](https://www.birelart.com/public/karts/modelli/pdf/1/TECHNICAL%20SPECS%20S19%20KZ.pdf) and [single-speed OK specifications](https://www.birelart.com/public/immagini/download/TECHNICAL_DATASHEET/S12_OK_BIRELART.pdf). Engine/jetting and centrifugal-clutch recording are supported by the [Rotax operating manual](https://www.rotax-racing.com/assets/uploads/Engines/KA_Operating-Manual_125MAX_en_2024_2024-12-06-081421_bkyi.pdf). The resulting shared schema is a manufacturer-neutral design inferred from these references.

7. **Road Course.** Both appear in the existing Road Course class list. The application retains its five disciplines. Development definitions total 38; the experimental selector has 49 total canonical classes, including the 11 existing definitions.

8. **Development-only access.** Both use `developmentOnly` and the existing user-ID-backed experimental gate: test designation, enabled beta master switch, `tester_kind = experimental`, and enabled `test_account_full_access`. No kart flag, email-based authorization, tier/admin bypass or development-mode bypass was introduced. Normal frontend selectors hide them and their forms deny unauthorized rendering.

Readback confirmed the test account's 15 existing setups, Pro Stock active class, null class-change timestamp and current metadata fingerprint were unchanged; zero rolled-back fixture rows remained. No login, logout, account reset, entitlement or flag change was performed.

10. **Cause.** The standalone walkthrough explicitly transitioned from class selection to its sheet screen. The protected onboarding preview previously displayed a completion placeholder. In the application, the dashboard initially chose home but its recent-route restoration could override that with a recent editor, and unnamed Custom Car restoration explicitly chose the editor. A restored named draft could also start the existing autosave interval while on landing.

While that selection request is active, a restored named draft does not autosave on landing; entering the editor explicitly resumes existing autosave. Failed initialization remains on selection with the existing error. Returning hydration does not issue this request, preserving intentional resume behavior outside the selection flow. No URL route, auth provider or unrelated tool routing changed.
