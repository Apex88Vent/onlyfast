## Tester-specific current offering

[RevenueCat explicitly recommends customer offering overrides for sandbox paywall testing](https://www.revenuecat.com/docs/tools/paywalls/testing-paywalls#3-override-a-customers-default-offering). An override assigns the offering as **that customer's current offering**, rather than changing the project default. [The API](https://www.revenuecat.com/docs/api-v2/customer) supports assignment and clearing. Median's ordinary `presentPaywall()` delegates to RevenueCatUI's current-offering presentation; the preserved Android plugin bytecode confirms the no-argument launcher path. Thus a tester override is the supported configuration route, without a portable named-offering argument or a new native bridge. iOS plugin linkage/API support was reviewed previously; actual display/callbacks still require its acceptance run. No override was assigned to prove this behavior on a device.

Use the UUID returned by verified LOCAL Supabase Auth and the server-managed experimental tester records, never an email, URL flag or localStorage privilege. The QA gate also refuses a full-access tester override, so server-confirmed membership is meaningful. The override is customer scoped, **not a sandbox-only security boundary**: it can affect that RevenueCat customer's aliases and both platforms/environments. Use designated synthetic IDs with no real-customer aliases/receipts. Keep the global current offering `default` unchanged. Apply an override only after the correct identified SDK/customer exists; cold-restart the native test app after propagation if cached offerings persist. Do not clear app data, initialize anonymously or repeatedly reconfigure to force cache changes. Clearing the offering override later does not cancel a subscription.
